For people writing open-source AID code with an AI assistant

OS-AID Review Kit

A set of checks and a written review record, both run on every commit. Code written with an AI assistant reaches a maintainer with a list of what was checked and the hash of the content each check saw.

Why it exists

Open-source automated insulin delivery projects have become wary of AI-written contributions. AndroidAPS stopped accepting AI-generated pull requests on 15 June 2026. The project gave two reasons: reviewing such code took maintainers longer than the model had taken to write it, and unverified code is a risk it will not accept.

The kit puts the checking on the person writing the code, before anything is pushed, and writes down what was checked. Each reviewed file is recorded with the git hash of the content that was reviewed. A maintainer can then compare that hash with the file in front of them and see at once whether it is the reviewed version.

What happens to one change

Suppose your assistant has changed the SMB limit logic in an AndroidAPS fork. That file can change a dose, so the kit puts it in the high tier. The tier is set by what a file can affect. Before the change can be committed, four things happen.

  1. The checks run on the staged files

    The language's linters, the secret scanner, the kit's static-analysis rules and the project's tests all run against what is staged. Each tool is described in the next section. The linters are run twice, on the file before the change and after it, and only a rise in a rule's count fails. An established project carries years of old findings, and none of them are put in front of you.

  2. A second model session reviews the diff

    The assistant starts a fresh session that did not write the change and gives it the diff and the project's review checklist (REVIEW.md), without its own reasoning. An important finding must be fixed before commit, after which the checks run again. Findings labelled nit or pre-existing are recorded and do not block.

  3. The review is recorded

    The record lists each file with its hash, each check with its result, each finding with what was done about it, and a plain account of what the change does and what could go wrong. High-tier records also state how to undo the change. The record is refused when a file changed after the checks ran or an important finding is still open. A high-tier record is also refused while any check has failed or not run, or when it gives no way back.

  4. The commit carries the evidence

    Git refuses the commit when any file in it is missing from a record in the form being committed. Once it goes through, the message gains these lines:

    Cap SMB at maxSMBBasalMinutes when the profile switches mid-cycle Review-Record: 20261120-181722-2337a36 Review-Tier: high Written-By: claude-opus-5-5 Reviewed-By: claude-opus-5-5, fresh context Human-Review: pending Review-Ledger: ~/.review-ledger

A push is checked the same way, for every branch in it. A person reviewing later runs review.py status to see what is waiting and whether anything has changed since its review, then review.py signoff to record a verdict. Sign-off is refused while the file differs from the reviewed one. The reviewer can force it, and the difference is then written into the record.

The developer does not run the pre-commit steps by hand. The assistant reads its instructions at the start of each session, so you ask for the change and it does the rest. A skipped step shows up as a refused commit, with a message naming what is missing. Work in progress can be committed with REVIEW_SKIP="reason", which writes the reason into the message; the push is then refused until the files have a record.

The tools it uses

The kit is a few Python scripts that call established open-source tools and keep the records. The versions below are the ones it was tested with.

"Checks" means the step the assistant runs before recording a review (review.py checks). The commit hook then confirms that a valid record exists and runs the secret scan again. Where the kit is committed to a project, the commit hook also runs the linters and the kit's Semgrep rules. The kit formats nothing: it never rewrites a file.

The linter for a language is needed only where you commit code in that language: Kotlin for AndroidAPS, Swift for Trio, JavaScript for Nightscout, Python for analysis code. A missing linter fails the checks, with a message naming the tool. A high-tier record is then refused, and where the kit is committed to the project the commit itself is refused.

Code quality and over-long code

Model-written code tends to be longer than the task needs. The kit treats this in two ways. Automatically, detekt, SwiftLint and Ruff flag functions that are too long or too complex, as listed above; these settings apply where a project has no linter configuration of its own, and a project's own rules take precedence. JavaScript has no automatic size check.

A linter can count lines and branches, but it cannot tell whether code was needed. That judgement is given to the second-model review, which is told to treat an oversized change as an important finding to be fixed before commit. Its instructions name four forms: an abstraction or option nobody asked for, a rewrite of a helper the project already has, dead or speculative code, and handling for cases that cannot happen.

A guard against skipping the checks

Git lets anyone skip its hooks, with git commit --no-verify for example. The kit therefore gives each supported assistant a guard that reads every shell command and file edit before it runs. It refuses --no-verify and its abbreviations, git commit -n, changes to where git looks for hooks, switching off the hook runner, and opting a project out. It also refuses hand edits to a review record and any sign-off entered by the assistant, since a sign-off belongs to the person who read the code. The refusal tells the assistant to run the review steps instead.

AssistantWhere the guard is addedInstructions file
Claude Code~/.claude/settings.json~/.claude/CLAUDE.md
Codex~/.codex/hooks.json; runs only after you approve it under /hooks~/.codex/AGENTS.md
Gemini CLI~/.gemini/settings.json~/.gemini/GEMINI.md

The guard reads the command as written. A script saved to disk and then run, or a deliberately obscured command, gets past it. Codex's documentation also says that some of its specialised tool paths skip hooks. The guard therefore stops an assistant drifting round the checks, and the record check at commit and push remains the control that binds. Other assistants are bound by their instructions and by those checks.

Setting it up on your machine

The steps are the same on macOS, Linux and Windows. You need Python 3.11 or newer and Git.

1. Install the tools

SystemCommand
macOSbrew install lefthook ktlint detekt swiftlint trufflehog semgrep trivy biome mypy ruff
LinuxInstall Homebrew from brew.sh, then the macOS line without swiftlint.
WindowsInstall Git for Windows and Node.js. Install Python too, ticking "Add python.exe to PATH" in the Python installer. Then in Git Bash: py -m pip install ruff mypy semgrep and npm install -g @biomejs/biome lefthook, and check with ruff --version && semgrep --version. Download trufflehog from its GitHub releases page and put it on your PATH. For Kotlin, also download ktlint and detekt-cli from their releases pages. Trivy is needed only for projects the kit is committed to.

2. Put the kit in your home folder

Save the kit folder you were sent as os-aid-review-kit in your home folder (~/os-aid-review-kit, or C:\Users\you\os-aid-review-kit on Windows).

3. Switch it on

In a terminal (Git Bash on Windows), naming only the assistants you use:

$ python3 ~/os-aid-review-kit/kit/global.py on --claude --codex --gemini

On Windows, type py in place of python3. From then on every commit and push on the machine goes through the checks. Each named assistant gets the guard, and the review steps are added to its instructions file without touching what is already there. Codex users then open Codex once, type /hooks and trust the review guard.

Nothing is added to your projects. The records are kept in ~/.review-ledger, which is a git repository of its own. Hooks your projects already use keep running, and merging from upstream needs no record for files your fork never changed. A project that sets its own hooks location, as husky does, is outside the checks; global.py on --scan ~ lists any. global.py off removes the hooks and the guard again.

To keep the records inside one project instead, so that they travel with its pull requests, run python3 ~/os-aid-review-kit/kit/install.py <project folder> --hooks and commit what it adds.

4. Check that it works

Make a small change and try to commit it without a review. The commit should be refused. Try the same from any graphical Git program you use, since some bundle their own copy of Git that may not run the hooks. On Windows, Git inside WSL is a separate installation and needs the kit switched on there as well.

What it does and does not establish

A record states that a review took place and what it covered. Its value depends on the reviewer, and a second model session misses things a person would catch. The kit makes the review visible and checkable, and tells the person reading safety-critical code which files to read and what has already been run against them, which leaves that reading to be done.

The kit has 123 automated tests, which run the Python, JavaScript and secret-scanning tools on Linux, macOS and Windows each time the kit changes. On 20 November 2026 all 123 passed on Linux and macOS; on Windows 119 passed and 4 were skipped because they test behaviour that does not exist there. The Kotlin and Swift linters are not part of that run. Repeated rounds of review by separate model sessions found defects in the kit, and each one now has a test that fails if it returns. The kit has gated AndroidAPS, Trio and Nightscout work on one developer's Mac since 20 November 2026. Linux and Windows are covered by the automated tests and have not yet been used for day-to-day work, and the Gemini CLI guard has been tested against its documented interface without a live session.
