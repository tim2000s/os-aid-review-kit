For people writing open-source AID code with an AI assistant

OS-AID Review Kit

Checks and a review record that run every time you commit. Code written with Claude, Codex or another model then reaches a maintainer with evidence of what was checked, and of the exact form in which it was checked.

What it is

Open-source automated insulin delivery projects are wary of AI-written contributions. AndroidAPS stopped accepting AI-generated pull requests on 15 June 2026, because reviewing such code took maintainers longer than the model took to write it, and because unverified code is a risk the project will not accept.

The kit moves the checking to the person writing the code, before anything is pushed, and writes down what was checked. Every reviewed file is recorded with the git hash of the exact content that was reviewed, so a maintainer can tell in seconds whether the code in front of them is the code that was reviewed.

What it does

Take a change your assistant has made to the SMB limit logic in an AndroidAPS fork. That file can change a dose, so the kit treats it as high tier. A file's tier depends on what it can affect; who or what wrote it plays no part. Before the change can be committed:

  1. The checks run on what is staged

    Linters, a secret scan, static-analysis rules and the project's tests. The linters fail only on problems the change adds, so you are never asked to fix the years of old findings an established project carries.

  2. A second model reviews the diff

    A fresh session that did not write the change reads the diff against the project's review checklist. Each finding is labelled important (must be fixed), nit or pre-existing, and every important one is fixed.

  3. The review is recorded

    The record lists each file with its hash, the checks and their results, the findings and what was done about each, a plain account of the change, and for high-tier code how to undo it.

  4. The commit carries the evidence

    A commit is refused if any file in it is missing from a record in exactly the form being committed. When it goes through, the message gains lines anyone can read:

    Cap SMB at maxSMBBasalMinutes when the profile switches mid-cycle Review-Record: 20261120-181722-2337a36 Review-Tier: high Written-By: claude-opus-5-5 Reviewed-By: claude-opus-5-5, fresh context Human-Review: pending Review-Ledger: ~/.review-ledger

Pushes are checked the same way, branch by branch. A person reviewing later runs review.py status to see what is waiting and whether anything has changed since its review, and review.py signoff to record their verdict. Sign-off is refused if the file differs from the one that was reviewed, unless the reviewer forces it, in which case the difference is written into the record.

You do not run these steps by hand. Your assistant reads its instructions at the start of each session, so you ask for the change and the assistant does the rest. If it skips a step, the commit is refused with a message saying what is missing. A work-in-progress commit can be marked with REVIEW_SKIP="reason": it goes through with that reason in its message, and the push is refused until the files have a record.

Code quality and over-long code

Model-written code tends to be longer than it needs to be. The kit looks for this in two ways.

LanguageAutomatic checks on size and complexity
Kotlindetekt: methods too long or too complex, too many parameters, blocks nested too deeply
SwiftSwiftLint: function length and cyclomatic complexity
PythonRuff: cyclomatic complexity above 10, and too many statements in one function
JavaScriptNo automatic size check; Biome looks for likely bugs, and size is left to the review

These apply where a project has no linter configuration of its own; where it has one, its own rules are used. Linters measure size, not need. The second-model review is told to treat an oversized change as an important finding, which must be fixed before commit. That covers an abstraction or option nobody asked for, a rewrite of a helper the project already has, dead or speculative code, and handling for cases that cannot happen.

A guard against skipping the checks

Git itself lets anyone skip the hooks. The kit therefore adds a guard to Claude Code that refuses, before they run, commands that would skip or switch off the checks: --no-verify in any spelling, git commit -n, changing where git looks for hooks, switching off the hook runner, or opting a project out. The guard also stops the assistant editing a review record by hand or entering a human sign-off, which only the person who read the code may do. The refusal tells the assistant to run the review steps instead. The matching is best-effort: it reads the command as written, so a script saved to disk and then run, or a few deliberately obscure forms, would not be caught.

The kit provides the guard for Claude Code only. Other assistants are bound by their instructions and by the checks on the shared repository.

Setting it up on your machine

Four steps, the same on every system: install the tools, put the kit in your home folder, switch it on, and tell your assistant. You need Python 3.11 or newer and Git. Of the linters, only those for the languages you work in are needed: Kotlin for AndroidAPS, Swift for Trio, JavaScript for Nightscout, Python for analysis code.

1. Install the tools

SystemCommand
macOSbrew install lefthook ktlint detekt swiftlint swiftformat trufflehog semgrep trivy biome mypy ruff
LinuxInstall Homebrew from brew.sh, then the macOS line without swiftlint swiftformat
WindowsInstall Git for Windows, Node.js and Python, ticking "Add python.exe to PATH" in the Python installer. Then in Git Bash: py -m pip install ruff mypy semgrep and npm install -g @biomejs/biome lefthook, and check with ruff --version && semgrep --version. Download trufflehog from its GitHub releases page and put it on your PATH. For Kotlin, also download ktlint and detekt-cli from their releases pages; both need Java 17 or newer.

2. Put the kit in your home folder

Save the kit folder you were sent as os-aid-review-kit in your home folder (~/os-aid-review-kit, or C:\Users\you\os-aid-review-kit on Windows).

3. Switch it on

In a terminal (Git Bash on Windows):

$ python3 ~/os-aid-review-kit/kit/global.py on --claude

On Windows, use py in place of python3. From then on every commit and push on the machine goes through the gate, and --claude adds the guard to Claude Code. The exception is a project that sets its own hooks location, as husky does; global.py on --scan ~ lists any. Nothing is added to your projects: the records are kept in ~/.review-ledger. Any hooks your projects already use keep running. Merging from upstream needs no record for files your fork never changed. global.py off switches both off again.

4. Tell your assistant

Add this line to the instructions file your assistant reads in every project: ~/.claude/CLAUDE.md for Claude Code, ~/.codex/AGENTS.md for Codex.

Before every commit, follow the review steps in ~/os-aid-review-kit/templates/AGENTS-block.md. Run review.py as sh ~/os-aid-review-kit/kit/py ~/os-aid-review-kit/kit/review.py, which works on every system; records go to ~/.review-ledger rather than into the project.

To keep the records inside one particular project instead, so they travel with its pull requests, run python3 ~/os-aid-review-kit/kit/install.py <project folder> --hooks and commit what it adds.

Check once that it is working: make a small change and try to commit it without a review. The commit should be refused. Try the same from any graphical Git program you use, since some bundle a Git of their own that may not run the hooks. On Windows, Git inside WSL is a separate installation and needs the kit switched on there as well.

What it does not prove

A record is an attestation, not a proof: a review is only as good as the reviewer. The kit makes the review visible and checkable. It does not replace a person reading safety-critical code, but it tells that person which files to read and what has already been checked.

The kit has 108 automated tests, which run on Linux, macOS and Windows with the Python, JavaScript and secret-scanning tools each time it changes; on 20 November 2026 all passed on all three, apart from three that do not apply on Windows. The Kotlin and Swift linters are not part of that automated run. The code has been through repeated rounds of review by a separate model session, and the defects found have tests that fail if they return. It has gated AndroidAPS, Trio and Nightscout work on one developer's Mac since 20 November 2026; Linux and Windows are covered by the automated tests but have not yet been used for day-to-day work.
